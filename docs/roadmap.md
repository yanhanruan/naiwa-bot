# 改造路线图

原计划共 10 个模块（由 codex 设计），下表是各模块范围与验收标准的摘要。“已定调整”各节记录 review 后确认的修改；与原计划冲突时，以调整为准，较新的调整优先。

## 产品定位（2026-11-17）

奶蛙的目标是**有个性的商业客服**：保留人设和语气，同时具备商业客服的要求，包括回答准确、可以转人工、隐私合规，以及以后支持多个客户（多租户）。后续各模块的设计都按这个定位取舍，见文末“商业客服待规划项”。

## 已定调整（2026-11-16 review）

适用于所有模块：

- **每个模块结束时部署并做真实 QQ 冒烟检查。** 线上机器人切到新代码，跑一份简短检查清单，避免线上与仓库越差越远。
- **尽早录制真实 SnowLuma 流量**（原始 OneBot 事件存成文件并脱敏），作为 Module 1 / 3 / 5 的测试数据。顺带核实：`time` 格式、`message_id` 在 SnowLuma 重启后是否稳定、@ 与引用段的实际格式。
  - Module 3 已核实：`time` 单位为秒；`message_id` 是有符号 32 位整数、不按顺序递增；@ 与引用段的格式见 [Module 3 导读](module-03-onebot.md)。`message_id` 在重启后是否稳定**仍未核实**。
- 使用 Git：每个模块在独立分支上完成，review 后再合并。

按模块：

- **Module 2**：定位为基础设施。存储方案已改为 PostgreSQL，详见下文“Module 2 设计要求”。
- **Module 2 之后：代号改为全局。** 现在模型看到的代号（`u1`、`u2`）按会话编号、只存在内存中。有了持久化存储后，改成**每个人一个全局、持久的代号**，同一个人在任何群和私聊里代号都相同，便于奶蛙认人。（Module 6 已实现。）
- **Module 3**：加入发送节流（非官方 QQ 客户端发得太快有封号风险）；加入以 `message.key` 关联的基础结构化日志（原属 Module 10，提前）。
- **Module 4**：加入成本上限（例如按会话限速、每日 token 上限）。
  - 已实现：每日花费上限按官方价格**估算金额**而不是 token 数（联网搜索按次计费，只限 token 会漏掉这部分），默认 20 元，用完后每次被叫到都回固定提示；按会话限速默认每分钟 10 次、每小时 120 次。见 [Module 4 导读](module-04-model.md)。
- **Module 7 之前的临时闸门**：只在私聊、被 @、或有人引用奶蛙的消息时回复。**已在切换时实现**（`replyToAllGroupMessages` 默认关闭），Module 7 完成后替换。**已由 Module 7 替换**：这个开关已删除，群里回不回改为按规则判断，见 [Module 7 设计稿](module-07-group-chat-design.md)。
- **Module 9**：精简。目前没有任何发布或私信动作的执行器，审批没有对象。先做持久化开关和 CLI 与运行中服务的通信；有需要审批的动作时再做审批。

## Module 6 设计要求：跨会话认人（已定：保守）

目标：奶蛙像真人一样认人，在不同群里都知道“这是同一个人”，但懂分寸。

> **实现情况（2026-11-17）**：按下面的要求实现。印象先用**规则印象**（QQ 昵称、熟悉程度，群里只按群聊互动算），不调模型；需要模型提炼的“兴趣、说话风格”以后单独做，届时再定私聊是否参与提炼（第 3 条）。短期历史存进数据库，24 小时内的当上文。详见 [Module 6 导读](module-06-context.md)。

记忆分三层：

| 层次 | 例子 | 可见范围 |
| --- | --- | --- |
| 对这个人的印象 | 昵称、兴趣、关系好坏、说话风格 | **跟着人走**：这个人在任何群或私聊发言时都可召回 |
| 会话里发生的具体事 | “他在群 A 说今天考试挂了” | **只在原会话**：群 A 的事只在群 A 召回 |
| 私聊内容 | 私聊里说的任何事 | **只在该私聊**：永远不进任何群 |

要求：

1. 新增一种“跟着人走”的可见范围（例如 `person:<用户key>`），专门存放对这个人的印象。它与 `conversation:<会话key>`（只在该会话可见）和 `private:<某人>`（某人的私事）语义不同，不复用已有前缀。
2. 默认采用**保守**策略：具体事件不跨会话。以后如需开放，按群单独设置（例如“他本人在场时可想起他在其他群的事”），默认关闭。
3. 从私聊提炼出的印象不能带有私聊细节，不能让群友推断出私聊内容。是否允许私聊信息提炼成印象，在设计时单独说明。
4. 取消 `self` 请求者“能看全部记录”的特权；角色自身记忆只按 `access === 'self'` 读取（Module 1 已在处理器层先做了过滤）。
5. 验收补充：同一个人在群 A 和群 B 发言，奶蛙在两边都能认出他（印象一致）；群 A 发生的具体事在群 B 不会被召回；私聊内容在任何群都不会出现。

## Module 2 设计要求：直接使用 PostgreSQL（2026-11-17 决定）

不再经过 SQLite。原因：

- 以后商业化必然要用 Postgres（多租户、多实例、高可用、云托管）。先做 SQLite 等于写两套实现、迁移两次数据。
- 真正的大改动是**存储访问从同步改成异步**（现在的 `fish.memory.retrieve` 等是同步的）。SQLite 能暂时不改，但迟早要改，在 Module 2 一次改完最省事。
- Postgres 的能力正好用得上：`JSONB` 存消息片段和 meta；行级安全（RLS）做租户隔离；`pgvector` 支持以后的语义记忆召回。

范围：

1. **异步存储接口**：覆盖记忆、事件、关系、角色状态，业务代码只依赖这个接口，不直接写 SQL。
2. **Postgres 实现**：驱动用 `pg`（node-postgres）。表结构用编号的 SQL 迁移文件（`migrations/001_init.sql`…）配合一个简单的迁移执行器管理。Module 5 / 6 / 9 需要的表通过各自的迁移添加。
3. **运行环境**：本地开发和部署用 `docker compose` 运行 Postgres，镜像版本固定。测试用 PGlite（编译成 WASM 的 Postgres，在 Node 进程内运行），`node --test` 不依赖外部服务。
4. **旧数据导入**：把 `data/naiwa` 的 JSON 导入 Postgres，包括 49 条 access 为 `self` 的旧情景记忆和以纯数字为键的旧关系记录。导入可验证（数量核对）、可重复执行；原 JSON 保留作为回滚依据。
5. **备份**：提供 `pg_dump` 备份与恢复脚本，并实际演练一次恢复。
6. 表结构预留租户字段（例如 `tenant_id`），先只有一个默认租户，多租户逻辑留给后续模块。

验收补充：

- 重启不丢数据。
- 两个进程同时写入（例如运行中的机器人和 CLI），互不覆盖；CLI 删除的记录不会被运行中的机器人写回。
- 数据库连接失败或数据异常时报错退出，不会以空数据启动，也不会清空数据。
- 旧 JSON 导入后数量一致。
- 全部测试在 PGlite 上通过；切换后做一次真实 QQ 冒烟检查。

## 记忆重新设计（2026-11-17 提出，2026-11-18 设计已定（第二版），2026-11-19 实现、通过真实 QQ 冒烟检查并合并进 main）

Module 6 解决了“别丢、别串、别泄露”，但“记什么、怎么想起来”仍是原型水平：

- 长期记忆把每次对话机械截成“某人说「前 60 字」→ 我「前 60 字」”，存的是原话，不是提炼过的事实；
- 召回靠字面重合，意思相近但用词不同的找不到；
- 印象只有昵称和熟悉程度，没有兴趣、说话风格。

讨论过程：

- 先后否决了两个方案：
  - “模型提炼事实 + 向量检索 + 按相似度分档去重”（Mem0 / Mutsumi 式），复杂在了不该复杂的地方；
  - “每个会话、每个人一份笔记，由模型定期整份改写”，改写会走样，字数上限会挤掉旧信息，每次改写都要花钱。
- 调研了 AI 伴侣产品、开源群聊机器人和学术方案的做法，两个否决都有依据。

**已定方向**：

- 原话不改；
- 模型只往后加带原话出处的短事实，不改写、不删除；
- 事实关于谁、在哪能用、什么时候删除，由程序决定；
- 私聊里提炼的事实只在该私聊用；
- 会话安静 10 分钟后提炼。

评审后又做了精简（第二版）：

- 事实只分 4 个项目：称呼、个人情况、近况、群事；只有群里说的称呼能带到别的群；
- 不记“承诺”（奶蛙还没有能真正办事的工具）；
- 回复时不做检索，相关事实全部放进提示，超过 20 条只放最新的；
- 原话保存期限仍是 7 天；
- 不做“不提炼名单”和未成年人处理（使用条款要求 18 岁以上）；
- 删掉 `memories` 表和它的可见范围规则，隐私规则只剩事实表的读取入口。

详见 [记忆重做（v2）设计](memory-v2-design.md)。线上已有的“前 60 字”情节记忆共 81 条，已于 2026-11-18 删除。

**实现情况（2026-11-19）**：在 `module-6-memory-v2` 分支实现，经过一次代码审查（修了 8 处，2 处留到以后，见设计文档“实现记录”），当天合并进 main。迁移 006 建了事实表和提炼进度表，删除了 `memories` 表；后台用 `deepseek-flash` 提炼；增加了运行锁，并把会被删除的数据都改成只经持锁连接写入；新增 `fish facts`、`fact-forget`、`forget-person` 三个命令。自动测试全部通过，运行锁和断线不写回这几项在真实 PostgreSQL 上测过；提炼评测 22 段对话，每次通过 21～22 段。真实 QQ 冒烟检查通过的项目：私聊记偏好、私聊内容不进群、群里的称呼跨群通用、群里约的事不跨群、引用奶蛙的话不会记成用户说的、机器人运行时拒绝按人删除、停机删除后奶蛙不再记得。

遗留：
- flash 模型偶尔会漏记该记的，或多记一条没说准的话，大约每 20 段错 1 段；
- 只有一个人约事时，模型会记成这个人的近况，不记成群事；
- 事件日志里的 `relationship.touched` 带着人的 key，`forget-person` 不删（2026-11-23 已补上）。

## Module 7 补充：连着发的一起看（2026-11-21 提出，2026-11-23 实现、通过冒烟检查并合并进 main）

Module 7 上线后发现两个问题：话没说完就回了（连发三句，先回第一句），“接着说”只看 1 分钟内的下一条，太死。

**已定方向**：程序只决定什么时候请模型看一眼；看的时候把这段时间的几句一起给它；回不回、回几条、回谁，由模型定。

- 每个群攒“一轮”：叫了它的人、或正在留意的人，停 7 秒没再说就一起看（从第一句算起最多 15 秒、最多 5 句），同一个群同一时间只有一轮在看；
- “接着说”改成“留意 30 秒”：叫过它或它回过的人，30 秒内说的话都请模型看；模型看了没回他，马上不再留意；
- 模型可以不回，也可以回几个人、一共最多 3 条，每条写明回谁；回了两个人以上，每条都引用对应那个人的话；
- 合并的只是模型调用：每句仍单独记进原话表，记忆提炼和按人删除照样对得上人；
- 私聊也走这一套；不改数据库。

详见 [Module 7 补充设计](module-07b-burst-merge-design.md)。

**实现情况（2026-11-23）**：在 `module-7b-burst-merge` 分支实现，新增 `src/runtime/round-queue.js`。自动测试全部通过；效果评测加了 5 段多人、多句的，14 段有明确答案的全部通过；新增 `npm run sim:group`，按真实时间间隔模拟两个群友跑一遍冒烟检查，22 项全部通过。QQ 冒烟检查发现并修了两处：

- “停 3 秒”太短：真人一句一句打，隔 4 秒左右很常见，三句被拆成三轮各回一次。试过“模型在想时他又补话就丢掉草稿重看”，代码太复杂，撤回；改成停 7 秒、最多 15 秒。代价是单问一句时，回复从大约 5 秒变成大约 10 秒。
- 回复里硬提“奶蛙”、正事后面再加一段玩笑：聊天行为准则加了“不加戏”一段。

合并前经过一次代码审查，修了 7 处（例如开头叫名字也开始留意，免得奶蛙在想的时候他补的话丢掉），见设计稿“代码审查以后改的”。当天合并进 main。

## 回复显得笨：第一步“听懂再说”（2026-11-23 调研、实现，通过 QQ 冒烟检查，合并进 main）

7b 冒烟检查时提出“奶蛙很笨”。先调研：线上 49 条模型写的回复里约 16 条笨，最多的是“看不全、连不起来”（被引用的那句看不到、记不住自己刚说的话、别人回第三个人时开头带了“奶蛙”就以为在叫它），其次是人设让它装傻、往自己身上扯，梗没听懂排第三。详见 [调研报告](naiwa-smartness-research.md)。

**已定（2026-11-23，你回复“可以开工了”）**，按报告的推荐做一个小模块：

- 人设改 8 处：去掉“迟钝”“经常一本正经地理解错”“自作多情”“不是一个客服”这些和“回答准确”打架的话，幽默放在说法上、不放在理解错上；最后一节不再叫“最高优先级”；
- 准则加一段“听懂再说”：连起来读、几个人聊同一件事当一件事回、带名字但在回别人不是叫你、读着别扭先想是不是梗，拿不准就搜。实现时在“想要什么”后面加了一个例子（“喝什么奶茶”“吃什么好”是让你推荐）：不加的时候，8 次里有 3～4 次答成自己喝什么、或者编“我最近喝得最多的是……”，加了以后 8 次都没有；
- “群里刚才在聊”从说明书挪到最后一条用户消息里、紧挨着这一轮，标题不再说“这些不是在跟你说话”；“开头叫名字”的说明加上“或者是在回别人”；
- 对话历史从 12 条放到 20 条；
- 效果评测加 5 段“听懂没有”的和 1 段“记不记得 14 条以前自己说的话”，群聊模拟加一项“是给建议，不是说自己喝什么”。

**口癖（2026-11-23 你在看图评测里提出，当天改了两轮）**：有人 @ 它只发一个表情包，它回“？我干嘛了”，显得凶。改法：

## Module 8：奶蛙的心情（2026-11-24 调研、设计、实现，通过 QQ 冒烟检查，合并进 main）

先做了一次调研（报告 `reports/数字生命心情机制调研.md`，不在仓库里）：没有主流产品公开做过“每日心情基调”；中文 QQ 圈最大的开源机器人 MaiBot 的心情功能重写约 4 次后删掉了；按人存情绪、好感会让奶蛙靠近《拟人化互动服务管理暂行办法》。据此和你的几轮回复定了做法，详见 [Module 8 设计稿](module-08-mood-design.md)：

- 一条心情线 5 档（很低落、有点低落、平常、开心、很开心），每天早上 5 点抽基调（平常 55%，负面不连着两天），运营可以用 `fish mood set` 改；
- 日内起伏由写回复的模型顺带判断（被夸、被谢、被骂、被挑衅都算），多写一行 `[心情 变好/变差 uN]`，程序拿掉不发；同一个人一小时只算一次、同一个群一小时最多 3 次，最多离基调一档，每 2 小时回一半；
- 每一档的语气和口癖放在 `persona/moods/`，平常没有文件，说明书和以前一字不差；心情任何时候都不屏蔽；
- 全局一份，不按群、不按人存；删掉了好感、备注两列和旧的心情代码，改关系时不再往事件表写带好感的记录（迁移 007）。

实现时修了两处：起伏会一直往回落，原来要攒满 0.5 才换档，两次永远差一点，改成 0.4 就换档；两个进程同时第一次建心情那一行，后建的会清掉先建的起伏，改成先建的为准。自动测试全部通过（真实 PostgreSQL 244 个连跑三遍）。

QQ 冒烟检查通过：当天抽到“有点低落”，问心情答“一般，有点提不起劲……”，推荐奶茶照样认真；被谢记了一次“变好”，心情标记没漏进回复和原话表。“同一个人一小时只算一次”在 QQ 里没测到（第二次夸时模型没写心情那一行），由自动测试覆盖。合并以后 main 上旧代码就跑不了（数据库少了好感那几列）。
