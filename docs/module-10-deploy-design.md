## 1. 现在的问题

都是看代码和本机运行情况时确认的：

| 问题 | 具体情况 |
| --- | --- |
| 奶蛙是手动跑的 | 一直是在某个工作区里用 `node --env-file=../naiwa-bot/.env bin/fish-bot.mjs` 手动起，输出接到一个管道上。开它的终端或会话一关，它就停了；崩了不会自己起来；Mac 重启后也不会起来 |
| 数据库一重启，奶蛙就一直停着 | 运行锁的设计是“持锁连接一断就立即退出”（这是对的，防止两个奶蛙同时写）。但退出以后没有人把它拉起来 |
| 日志事后查不到 | 日志只打到标准输出，不落文件。群友下午说“奶蛙上午没理我”，上午的日志已经没了 |
| 日志里找不到“那一句” | 没叫到奶蛙的群消息只在 `debug` 级别记，平时看不到；日志里也没有发言人。知道“哪个群、谁、几点”，也对不上是哪条 `messageKey` |
| 只知道“现在”，不知道“当时” | Module 9 的 `naiwa status` 只看奶蛙现在连没连上 SnowLuma；昨天几点掉过线、重启过，没地方查。而且“奶蛙连着 SnowLuma”和“QQ 小号在线”是两回事 |
| 新环境没法照着装 | 步骤散在 README、`migration.md`、Module 2 导读里；`Dockerfile` 只给守护进程用，没打包人设文件；SnowLuma 在另一个目录、用的是 `latest` 镜像，仓库里没写怎么从零装 |
| 备份全靠手动、不过期 | 主工作区 `naiwa-bot/backups/` 里有 7 个开发期的备份文件，没有自动备份，也没有保留期限 |

## 2. 做完以后看到什么

每次查询都分两块：**现在**（奶蛙此刻的状态）和**当时**（你问的那段时间里发生了什么：掉线、恢复、重启，和那个人说的每一句，按时间排在一起）。

### 例 1：群友说“奶蛙刚才没理我”

```
$ npm run trace -- 群 123456 QQ 10001 14:05

现在：奶蛙在跑（今天 09:12 启动，版本 317d698）· 连着 SnowLuma · QQ 小号在线
当时（14:00～14:10）：奶蛙一直在跑，连接正常，QQ 小号在线
群 123456 里 QQ 10001 说了 4 句：

  14:04:12  没叫奶蛙（不是 @、不是引用它、没用“奶蛙”开头，也不在留意中）→ 不看
  14:05:30  @ 了奶蛙 → 攒进一轮 → 14:05:38 开始看 → 模型 9.2 秒 → 14:05:48 发出 ✓
  14:06:02  在留意中 → 模型看了，觉得不用回 → 不出声
  14:08:40  @ 了奶蛙 → 这个群当时设成了“不说话” → 不出声
```

最后一句是很常见的情况：他确实 @ 了，但这个群被 `naiwa group` 调成了“不说话”（或者“只回 @”时他没 @）。记的是当时的设置，事后改了开关也不影响。

### 例 2：群友说“昨天晚上 @ 了奶蛙，没理我”

```
$ npm run trace -- 群 123456 QQ 10001 昨天 21:30

现在：奶蛙在跑 · 连着 SnowLuma · QQ 小号在线
当时（11-25 21:20～21:40）：
  21:18:05  ⚠ QQ 小号离线
  21:52:40  QQ 小号恢复在线
群 123456 里 QQ 10001：这段时间一条都没收到。
原因多半是：21:18～21:52 QQ 小号离线，那段时间群消息到不了奶蛙。
```

查不到消息时，trace 按当时的记录说清楚是哪种情况：

| 当时的记录 | trace 怎么说 |
| --- | --- |
| QQ 小号离线 | “21:18～21:52 QQ 小号离线，群消息到不了奶蛙” |
| 奶蛙连不上 SnowLuma | “21:18～21:52 奶蛙和 SnowLuma 断开了，一直在重连” |
| 奶蛙停着（有正常退出或意外退出的记录） | “21:10 奶蛙正常退出，22:05 才重新启动，中间没在跑” |
| 奶蛙在跑、连接正常，就是没有他的消息 | “这段时间奶蛙在跑、连接正常，没收到他在这个群的消息”（多半是发错群、记错时间。他要是在 `naiwa ignore` 的不理名单里，他的话会照常列出来，标“在不理名单里”） |
| 这段时间一行日志都没有 | “这段时间没有记录：上一行是 02:41，下一行是 07:05。可能是 Docker 没开、Mac 在睡眠” |
| 超过 14 天 | “日志只留 14 天，11-10 的已经删了” |

  14:05:30  @ 了奶蛙 → 今天的模型花费到了上限（20 元）→ 发了固定提示

## 3. 部署怎么做

### 3.1 奶蛙放进 docker compose

`docker-compose.yml` 加一个 `bot` 服务，和 `db` 在一起：

- 用仓库里的 `Dockerfile` 构建（改成默认跑 `bin/fish-bot.mjs`，把 `persona/` 也打包进去；构建时把 git 提交号放进环境变量 `GIT_COMMIT`，Module 9 的 `naiwa status` 已经会先读它）；
- 读同目录的 `.env`；数据库地址在 compose 里改成 `db:5432`；SnowLuma 还在本机另一个 compose 里，奶蛙容器加入它的 Docker 网络，用 `ws://snowluma:3001` 连（不改 SnowLuma 容器本身）；
- `restart: unless-stopped`：崩了、数据库断了退出、Mac 重启后 Docker 起来，都会自己回来；
- `init: true`：容器里由一个很小的 init 进程当 1 号进程，奶蛙不当 1 号进程，被杀掉时能像真崩溃一样退出、被拉起来（也方便第 7 节演练“崩了”）；
- 停容器时给 15 秒（奶蛙退出时最多等 10 秒处理完手上的消息）；
- 日志目录挂到宿主机的 `./logs`（见第 4 节），容器重建也不丢。

守护进程（`fish` 服务）还是可选的，用同一个镜像、换个启动命令。

另外两处小改：

- compose 文件里写死项目名 `naiwa-bot`：在任何工作区里跑 `scripts/backup.sh`、`npm run trace`，找到的都是同一个数据库，不会悄悄建出第二个空库；
- `package.json` 加 `npm run bot`（在宿主机直接跑，冒烟检查用）。

**SnowLuma 不并进来**：它的 QQ 登录状态存在它自己 compose 的卷里，换个 compose 项目卷名就变了，要重新扫码。正在跑的那个不动；新环境文档里给一份 SnowLuma 的 compose 写法，镜像按摘要固定到你本机现在这个版本。

### 3.2 平时怎么切换

| 场景 | 怎么做 |
| --- | --- |
| 正式运行 | `docker compose up -d`（数据库 + 奶蛙 + 每日备份 + 提醒） |
| 更新代码 | main 上 `git pull` 以后 `docker compose up -d --build bot` |
| 冒烟检查某个分支 | `docker compose stop bot` → 在工作区里 `npm run bot` → 测完 Ctrl-C → `docker compose start bot` |
| 奶蛙停着时查日志 | `npm run trace …` 照常能用（只读 `./logs`）；没装 Node 的机器用 `docker compose run --rm --no-deps bot node scripts/trace.mjs …`，临时起一个容器读日志，不需要奶蛙和数据库在跑 |
| 误开了两个 | 后开的那个拿不到运行锁，直接拒绝启动（已有） |

主动停机（`docker compose stop`、Ctrl-C）时奶蛙会在心跳表里写“正常退出”，提醒服务看到这个就不打扰你；冒烟检查期间不会收到“奶蛙没在跑”。

### 3.3 新环境文档

新写 `docs/deploy.md`，把散在各处的步骤收到一处，每一步写清楚“看到什么算成功”：

1. 装 Docker，自己拉好镜像（`postgres:18-alpine`、`node:22-alpine`、SnowLuma 固定的那个版本）；
2. 起 SnowLuma，在 noVNC 里扫码登录 QQ 小号，在 WebUI 里拿到 OneBot token；
3. 复制 `.env.example` 成 `.env`，填 DeepSeek key、OneBot token、数据库密码、提醒用的主号和 Bark 地址；
4. 先只起数据库、跑迁移：`docker compose up -d db`，`npm run db:migrate`；
5. **在奶蛙连 QQ 之前先设好运营设置**：`naiwa group default …`（没单独设置的群说不说话）、`naiwa group <群号> …`、`naiwa ignore add …`、`naiwa budget set …`，然后 `naiwa status`、`naiwa groups` 看一遍。新库默认所有群都“说话”，不先设好的话，奶蛙一连上就会在所有群里说话；
6. `docker compose up -d`；
7. `npm run trace`：看到“在跑 · 连着 SnowLuma · QQ 小号在线”；
8. 用主号私聊奶蛙一句，它回了；`npm run trace -- 私聊 <主号>` 能看到这一句。

`migration.md` 里讲 Docker 和备份的部分并进去，README 的“快速开始”指向它。

## 4. 日志和排查

### 4.1 日志多落一份文件

- 设了 `LOG_DIR` 就往里写：每天（北京时间）一个文件，例如 `logs/bot-2026-11-26.jsonl`，一行一个 JSON；
- 文件里总是记到 `debug` 级别（没叫到奶蛙的消息也记），终端和 `docker logs` 还是按 `LOG_LEVEL`，不会被刷屏；
- 每天清理一次，超过 14 天的文件删掉；文件只有本人能读；
- 在工作区里跑也写到同一个目录（`.env` 里写绝对路径），trace 才找得全。

日志的规矩不变：**不写聊天正文、回复内容、昵称、token**。

### 4.2 日志里补两样东西

| 补什么 | 为什么 | 例子 |
| --- | --- | --- |
| 每条消息带上发言人 | 按“谁说的”找得到那一句 | `messageKey=…:group:123456:message:-998 sender=qq:user:10001` |
| 没叫到奶蛙的消息也记一行 | “没理我”最常见的原因就是他没叫它，或者群被设成了不说话 | `message.ignored reason=not_addressed`、`reason=group_off` |

量：每条群消息一行，大约 200 字节；一天 5000 条群消息也就 1 MB。

“当时”要用到的记录日志里已经有了，不用新加：奶蛙启动、正常退出、因数据库断开退出（`bot.started`、`bot.stopping`、`bot.run_lock_lost`），和 SnowLuma 连上、断开（`onebot.connected`、`onebot.disconnected`），QQ 小号离线、恢复（`onebot.bot_offline`、`onebot.bot_online`）。现在只是没存下来，存进文件以后就能按时间查。

### 4.3 `npm run trace`

`scripts/trace.mjs`。逐句记录和“当时”只读日志文件，奶蛙、数据库都停着也能查；只有“现在”那一行要读数据库里 Module 9 的心跳表 `bot_status`，连不上就说“数据库连不上”，其余照常（例 6）。

- `npm run trace`：整体情况（例 4）；
- `npm run trace -- 群 <群号> [QQ <号码>] [日期] [时间]`：这个群（这个人）在那个时间前后 10 分钟说的每一句走到了哪一步，和这段时间里的掉线、恢复、重启记录排在一起（例 1～3）。日期可以写“昨天”“前天”或 `11-25`，不写就是今天；时间不写就是最近 30 分钟；
- `npm run trace -- 私聊 <号码> [日期] [时间]`：同上；
- `npm run trace -- <messageKey>`：一条消息的全部日志原样列出来，给我排查用。

“走到了哪一步”就是把同一个 `messageKey` 的几行日志按时间排起来，每种结果配一句中文（没叫它、群设成了不说话、太旧、模型不回、花费上限、余额不足、限速、发送失败……），这张对照表就是现在已有的 `reason` 和 `outcome`。

“现在”那一行：在不在跑、连没连着 SnowLuma、跑的哪个版本，读 Module 9 的心跳表；QQ 小号在不在线，心跳表里没有，看日志里最近一次离线、恢复的记录。

## 5. 备份和恢复

### 5.1 每天自动备份

compose 加一个 `backup` 服务：用和数据库同一个 `postgres:18-alpine` 镜像（不用另拉），每天北京时间 4:00 做一次 `pg_dump`，校验能读出目录才算成功，放进 `./backups`，删掉 7 天前的。手动的 `scripts/backup.sh` 照旧能用。

备份失败会在它自己的日志里记一行；`npm run trace` 的整体情况里显示“最近一次备份”是什么时候；超过一天半没有新备份会提醒你（第 8 节）。

### 5.2 不停奶蛙的恢复演练

新加 `scripts/restore-drill.sh [备份文件]`（不写就用最新的）：

1. 在同一个 PostgreSQL 里建一个临时库 `naiwa_drill`；
2. 把备份恢复进去，任何一步出错就算失败；
3. 检查：迁移版本是不是最新的那个、几张主要的表各有多少行；
4. 删掉临时库，打印结果，例如“11-26 04:00 的备份可以恢复：迁移到 008，原话 1,234 行，事实 56 条，代号 18 个”。

不碰线上库，奶蛙照常跑。`backup` 服务每天备份完顺手跑一次，结果也写进 trace 的整体情况。

### 5.3 真恢复（线上库）

还是用现有的 `scripts/restore.sh`（奶蛙没停会拒绝、恢复前先备份当前库、提醒对之后按人删除过的人重新删）。只是文档里的停机命令改成 `docker compose stop bot`，恢复完 `docker compose start bot`。

## 7. 怎么验证

### 提醒怎么做

compose 加一个 `alert` 服务：用奶蛙同一个镜像，每 5 分钟查一次，崩了自己起来。不在 Mac 上装定时任务。它自己去查，不靠奶蛙进程，所以奶蛙死了也能报。

| 什么事 | 怎么查 | 提醒的话（例子） |
| --- | --- | --- |
| QQ 小号离线，或 SnowLuma 没响应，超过 5 分钟 | 直接问 SnowLuma | ⚠ 奶蛙：QQ 小号 13:50 起离线，去 noVNC 重新扫码 |
| 奶蛙在跑，但连不上 SnowLuma 超过 5 分钟 | Module 9 心跳表里的“连没连上、从几点起” | ⚠ 奶蛙：13:50 起连不上 SnowLuma，群里叫它都没用 |
| 奶蛙意外停了超过 5 分钟 | 心跳表：心跳停了，又没写“正常退出”。你主动停的不提醒 | ⚠ 奶蛙：10:31 起意外停了，没有自己起来 |
| 数据库连不上超过 5 分钟 | `alert` 自己连数据库 | ⚠ 奶蛙：10:31 起连不上数据库 |
| 超过一天半没有新备份，或恢复演练失败 | `./backups` 里最新的文件和演练结果 | ⚠ 奶蛙：最近一次备份是前天 04:00 |
| 今天的花费到了上限（现在是 20 元） | 今天的花费表 | ⚠ 奶蛙：今天花到 20 元上限了，零点前只回固定提示 |
| DeepSeek 账户余额低于 ¥50 | 每 5 分钟问一次 DeepSeek 的余额接口（不花钱） | ⚠ 奶蛙：DeepSeek 余额只剩 ¥38，记得充值 |
| DeepSeek 账户余额用完 | 同上 | ⚠ 奶蛙：DeepSeek 余额用完了，奶蛙现在只回固定提示，充值后自动恢复 |

- “今天到上限”和“账户没钱”是两回事：前一个是奶蛙自己定的每日上限，第二天零点自动恢复；后一个是 DeepSeek 账户里真没钱了，要你去充值。余额线 ¥50 写在 `.env` 的 `ALERT_BALANCE_CNY` 里，可以改。余额接口 2026-11-26 核实过（`GET /user/balance`，返回是否可用和人民币余额）。
- 每条提醒两路都发：
  - **QQ 私聊**：经 SnowLuma 用小号发给 `.env` 里的 `ALERT_QQ`（你的主号）。QQ 小号掉线时这一路发不出去，就跳过；
  - **推到手机**：iPhone 上装 Bark App，把 App 里显示的推送地址填进 `.env` 的 `ALERT_BARK_URL`。小号掉线靠这一路。
- 提醒的话只有发生了什么、从几点起、怎么处理，不带群号、QQ 号，也不带聊天内容（推送会经过第三方）。
- 同一件事只提醒一次，恢复了再说一声（“✓ 奶蛙：QQ 小号 14:20 恢复在线”）。提醒发没发出去记进日志，trace 里看得到。
- 这条私聊是发给你本人的运维提醒，不是替你给群友发消息，所以不用等 Module 9 说的“发消息的动作”。

还管不到的：Docker Desktop 没开或 Mac 睡眠时，这个服务也跟着停，就没有提醒了；醒来以后 trace 会如实显示“这段时间没有记录”。

## 9. 不做的

这一版交付命令行排查（trace）和手机提醒。下面这些明确不做：

- **网页管理界面、给监控读的 `--json` 输出**：Module 9 把这两项留给了 Module 10。这一版先不做，以后有第二个人要管、或者要接监控系统时再做；
- Prometheus、Grafana、集中日志、告警平台：一台机器一个奶蛙，日志文件加 trace 加手机提醒够用；
- 多实例、高可用、云托管（多租户以后再说）；
- 把 SnowLuma 并进奶蛙的 compose；
- 自动更新代码（还是手动 `git pull` 加 `up --build`）；
- Mac 睡眠、Docker 没开时的提醒（见第 8 节）。
