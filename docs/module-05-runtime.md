# Module 5 导读：消息处理运行时

这个模块管的是收到消息之后、发出回复之前的这一段调度：

- 谁先处理；
- 能不能同时处理；
- 重复收到的消息怎么办；
- 发送失败了怎么办；
- 退出和重启时手上的消息怎么办。

代码在 `src/runtime/`（会话队列、消息记录）和 `src/qq-handler.js`（把它们接进处理流程）。

## 为什么要改

| 问题 | 怎么发生的 |
| --- | --- |
| 连续消息覆盖上下文 | 消息是并发处理的。生成回复时取对话历史的快照，记录时用“快照 + 这一轮”整个替换。同一会话里两条消息挨得近时，第二条看不到第一条的对话，写回时还会把第一条那一轮冲掉。已用测试复现：同一会话的 3 条消息同时在调用模型 |
| 后一条答非所问 | 同样因为并发。用户先说“我想退货”，紧接着发“订单号 123”，第二条开始处理时第一条还没回复完，模型不知道前文 |
| 重复事件重复回复 | 没有去重，同一事件收到两次就回复两次 |
| 发送失败没留下记录 | 发送失败时只是不写记忆，没有任何地方记下“这条没发出去”。断线期间没发出去的回复，重连后也不会补发 |
| 退出时中断消息 | Ctrl-C 后立即断开连接、关闭数据库，正在处理的消息直接中断，也没有记录 |

## 现在怎么做

### 1. 同一会话逐条处理

`src/runtime/conversation-queue.js` 给每个会话（一个群或一个私聊）排一个队：

- 按到达顺序逐条处理。前一条的回复发出、写进历史之后，才开始下一条，所以后一条看得到前一条的对话。
- 不同会话并行，同时最多 4 个会话在处理。
- 每个会话最多排队 5 条（不含正在处理的那条）。满了新消息直接丢弃，免得有人刷屏时越排越长。
- 多个会话都在等空位时轮流来：一个会话处理完一条、还有下一条，就排到其他在等的会话后面，不会被一个刷屏的会话占满。

代价是：同一个群里几个人同时 @ 奶蛙，回复会一条一条地来，每条通常 5～15 秒。

### 2. 重复的消息只处理一次

每条叫到奶蛙的消息在 `inbound_messages` 表里记一行，主键是消息 key（机器人账号 + 会话 + 消息编号）：

- 24 小时内同一条消息第二次出现，直接跳过，记一条 `message.duplicate`。
- 同时到达两次时，数据库主键保证只有一次能“认领”成功。重启以后再收到也能识别。
- 超过 24 小时的旧记录允许重新认领：消息编号是 32 位有符号整数，很久以后可能被重新使用。
- 只记录叫到奶蛙的消息。没叫到的本来就不处理，也不记录。

### 3. 太旧的消息不再回复

消息超过 3 分钟（按消息自己的时间）就不回复：

- 收到时就已经超时的直接跳过，状态 `skipped`，例如奶蛙停机期间积压的消息；
- 排队期间超时的丢弃，状态 `dropped`。

回复几分钟前的话已经没有意义，还容易接错话。

### 4. 发送失败：只在肯定没发出时补发一次

Module 3 把发送失败分成了“肯定没发出”（`not_sent`）和“结果未知”（`unknown`）。这里按它决定要不要重发：

| 情况 | delivery | 怎么做 |
| --- | --- | --- |
| 没连上 OneBot（`NOT_CONNECTED`） | `not_sent` | 等重连，最多 20 秒，连上后再发一次 |
| SnowLuma 明确拒绝（`ACTION_FAILED`，例如被禁言、风控） | `not_sent` | 不重发。重发多半还是失败，频繁重试还可能加重风控 |
| 节流队列满或预计排队太久 | `not_sent` | 不重发。失败的原因本来就是发得太多 |
| 超时、等响应时断线 | `unknown` | 不重发。消息可能已经发出，重发会让对方收到两条 |

不管哪种失败，都不写对话历史和记忆。消息记录里写 `send_failed` 和 `delivery`，不会被记成“已回复”。

### 5. 如实记录每条消息的结果

`inbound_messages` 里每条消息的状态（`src/runtime/inbox.js`）：

| 状态 | 含义 |
| --- | --- |
| `queued` | 已收到，排队中 |
| `processing` | 正在处理 |
| `replied` | 发出了模型的回复 |
| `notice` | 发出了固定提示（模型失败、花费上限、会话限速、内容过滤，见 Module 4） |
| `silent` | 按规则不回复（同一段限速时间里第二次及以后被拒） |
| `send_failed` | 没发出去；`delivery` 说明是肯定没发出还是可能已发出 |
| `dropped` | 没处理：排队太久（`stale`）、队列已满（`queue_full`）或正在退出（`shutting_down`） |
| `skipped` | 收到时就已经太旧 |
| `abandoned` | 处理到一半时进程退出或重启 |

同时记录 `outcome`（与日志 `message.done` 的一致）、错误码、发出的消息编号和发送次数。只存标识和结果，不存聊天内容。记录保留 30 天，每天清理一次。

查最近一小时每种状态各有多少条：

```bash
docker compose exec db psql -U naiwa -d naiwa -c "SELECT status, outcome, count(*) FROM inbound_messages WHERE received_at > now() - interval '1 hour' GROUP BY 1, 2 ORDER BY 3 DESC"
```

### 6. 退出与重启

- **Ctrl-C**：先停止接收新消息，等手上的处理完（最多 10 秒），再断开 OneBot、关闭数据库。等待期间再按一次 Ctrl-C 立即退出。
- **启动时**：上次退出时还在排队或处理中的消息标为 `abandoned`，日志里有一条 `runtime.recovered` 警告写明条数。不会补回复：那些消息多半已经过时。

### 7. 日志

| 事件 | 级别 | 说明 |
| --- | --- | --- |
| `message.duplicate` | 信息 | 重复收到的消息，已跳过 |
| `message.skipped` | 信息 | 收到时已经太旧 |
| `message.dropped` | 警告 | 排队太久、队列已满或正在退出，`reason` 写明是哪种 |
| `send.retry_wait` | 警告 | 没连上 OneBot，等重连后再发一次 |
| `runtime.recovered` | 警告 | 启动时发现上次没处理完的消息 |
| `runtime.stopped` | 警告 | 退出时还有消息没处理完 |
| `inbox.failed` | 错误 | 读写消息记录失败。不影响聊天：读失败时按新消息处理 |

`message.done` 新增 `queuedMs`（排队等了多久）和 `sendAttempts`（发了几次，大于 1 时才写）。发送失败时带 `delivery`。

### 8. 参数

默认值在 `src/qq-handler.js` 的 `RUNTIME_DEFAULTS`，创建处理器时可以覆盖：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `maxConcurrent` | 4 | 同时处理的会话数 |
| `maxPendingPerConversation` | 5 | 每个会话最多排队几条 |
| `maxAgeMs` | 3 分钟 | 消息超过这个时间就不回复 |
| `sendRetryWaitMs` | 20 秒 | 没连上 OneBot 时最多等多久重连 |

## 本模块没做的

- **合并连续消息一起回复**：现在每条叫到奶蛙的消息各回复一次。群里热闹时少插话属于 Module 7。
- **重启后保留上下文**：对话历史、会话内代号、“奶蛙发过哪些消息”仍只在进程内，重启后丢失（Module 6）。
- **补回复中断的消息**：重启后只做标记，不补发。
- **多个机器人进程同时运行**：启动时的中断恢复假设同一租户只有一个进程。
- **`message_id` 跨 SnowLuma 重启是否稳定**：仍未核实。去重只看 24 小时内的记录，即使编号被重新使用，影响也只是极少数消息被误判为重复。
